# Chat branching: DeepSeek Harness and this repo

Research date: 2026-10-22

## Scope and identification

“DeepSeek Harness” refers here to DeepSeek’s public open-source agent harness, `deepseek-ai/deepseek-harness`, advertised on DeepSeek’s own Harness page as a desktop app or web UI built on Cordis. It is a different product from the consumer DeepSeek chat site and from DeepSeek’s model APIs. This distinction matters: the API docs describe what the model endpoint receives, not the chat product’s UI or Harness session behavior. ([DeepSeek Harness product page](https://www.deepseek.com/en/harness/); [official repository](https://github.com/deepseek-ai/deepseek-harness))

## Findings from official sources

- **Model context is a selected projection.** The Harness session subsystem describes a durable append-only event log. Message-producing events mark how they enter an ordered “surface”; `Session.deriveMessages()` projects that surface into the `Message[]` sent to the model. Normal chat messages append. Surface replacement shadows a span in future model inputs while retaining the underlying log records; compaction is the documented replacement use case. The projection is cached, returned as a fresh array, and frozen. ([Session subsystem: derived history and surface operations](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session.md#derived-history-derivemessages-and-deriveeventmessage); [session package: derived history](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/session/README.md#derived-history))
- **Branching creates a child Session from a boundary.** `SessionStore.fork(source, boundary)` creates a live child seeded with the source events through an inclusive stable boundary, requires a between-turn boundary, and records parent/seed metadata. The Client workspace documentation describes the UI fork action as a separate peer conversation, from either the latest completed turn or a message in its containing completed turn. The source Session remains a separate item. ([Session subsystem: live-session fork API](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session.md#live-session-fork-api); [Client workspace](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-workspace/README.md))
- **Version navigation and user-message editing are not established as core behavior by the reviewed official docs.** The official UI Chat package documents rendering Session nodes and completed-turn actions; together with the Session docs it establishes Session-level forks and surface replacement mechanics, but not an in-transcript `<i/N>` version pager or an in-place edit/resend contract. Surface `replace` is a lower-level projection operation documented for compaction; it should not be treated as proof that the stock UI edits a user message that way. Community plugins advertise edit/regenerate/version-pager features, which is evidence that these are plugin behaviors, not evidence of core behavior. ([Official UI Chat package](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/ui-chat/README.md); example explicitly third-party plugin: [dsh-webchatlike](https://github.com/cindyguyuehu123/dsh-webchatlike))
- **Stop is cancellation; retry is a separate operation.** The official Session Controller documents cancellation as requiring live state and exposes prompt/cancel/fork lifecycle operations; the Session event model distinguishes aborted turns from errors and completed turns. A stop action therefore needs to settle against the Session, not merely hide a spinner. The reviewed official API docs do not specify a user-facing “retry this answer” operation. Do not equate model-internal retry records (`llm/retry`) with user-triggered answer regeneration. ([Session Controller](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/api/session-controller/README.md); [Session subsystem: turn end reasons](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session.md#why-a-turn-ended-turnendreasonmap))
- **The DeepSeek model APIs are stateless with respect to conversation state.** DeepSeek’s official multi-round Chat Completions guide says the client sends the accumulated message history on each request; its Responses API says conversations are not stored server-side and the full history must be sent. Thus the application/harness owns which branch is serialized into each next request. ([Multi-round Conversation](https://api-docs.deepseek.com/guides/multi_round_chat); [Responses API](https://api-docs.deepseek.com/api/create-response/))

## Read-only comparison with this repo

The current `feat/chat-experience` checkout already models branches explicitly:

- `backend/src/modules/chat/chat.service.ts` lists all nodes but builds `selectedPathIds` from the persisted selected node’s ancestry. Generation derives prior context from `buildMessagePath(...)`, not globally newest rows. Editing creates a fresh user sibling under the edited node’s parent; regeneration creates a fresh assistant sibling under the existing user. Selection now follows durable preferred-child choices to restore the complete remembered descendant path, including nested user and assistant versions. The initial implementation resolved only a direct assistant reply and could not remember inactive branch choices.
- `frontend/src/features/notebook-chat/hooks/use-chat-panel.ts` hydrates the SDK transcript from `selectedPathIds`; a branch switch posts selection and refetches history. Edit truncates the SDK transcript before the edited user turn and submits a fresh user message. The transport sends the current SDK messages plus explicit branch intent (`parentMessageId`, `editMessageId`, or `regenerateMessageId`).
- `docs/chat-branch-api-contract.md` records the intended contract, including server-authoritative selected endpoint and retry semantics after a failed/cancelled stream.

This architecture is directionally consistent with the Harness rule that the visible conversation and model context should be projections of the same selected path. It differs in persistence shape: this app stores a relational message tree and selected endpoint; Harness records an append-only event log and derives a surface.

## Recommendations for the reported branch-mixing symptom

1. Keep one canonical selected endpoint/path as the source for both rendered transcript and request construction. On branch selection, update the active path synchronously from the server’s returned selected endpoint (or hold generation until the path refetch has landed); do not let the SDK’s old in-memory `messages` array define the next request after navigation.
2. For edit, derive the new path from the edited node’s parent, create a new message identity, and submit only `ancestry(parent) + edited user`. Keep the previous node and descendants as another selectable branch.
3. For regeneration, submit the existing user node’s ancestry and content, then persist the new assistant as a sibling. For retry of an unpersisted/failed request, reuse the same user identity only when server validation proves it is the same request and parent; otherwise reconcile history first.
4. Treat stop as a durable state transition. Preserve any partial answer as a stopped outcome, keep the selected endpoint at the user node if that is the application’s policy, and do not allow a concurrent branch switch or retry to race with an unsettled stream.
5. Make branch/version controls derive from server sibling ordering and endpoint selection. The message displayed after switching must be the exact path serialized into the following model request.

These are architectural recommendations informed by the official Harness/API behavior and this repository’s current code; they are not claims about hidden or proprietary DeepSeek implementation details.

## Evidence limits

The Harness is in public preview and its docs/source evolve on `master`; this note captures the public documentation reviewed on the research date, not a guarantee about every released build. The official sources reviewed do not fully specify stock UI behavior for editing, in-message version switching, or user-initiated regeneration/retry. Third-party plugins and user discussions are not treated as authoritative descriptions of the official product. DeepSeek API behavior alone cannot establish UI semantics.
